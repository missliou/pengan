# 三阶段智能体管线契约（decision → generate → verify）v1

本文件是 gateway 侧与原生 ArkTS 侧并行开发的**唯一接口基准**。两侧各自实现，只允许按本文件的字段名、枚举值、语义对接；任何一方要改契约，必须先回报 lead，由 lead 更新本文件并通知另一方。

## 1. 为什么是这个形状

赛题要求 Agent 具备任务规划、工具调用、记忆、主决策四项能力，且必须端云协同、结果在原生界面可视化。本管线把「主决策 + 规划 + 自我审核」拆成三次独立的模型调用，由 gateway 串起来，原生端只消费结构化的结果卡片：

- **decision（决策）**：模型只判断"现在该干什么、风险多高、有多大把握"，不产出可执行步骤。
- **generate（生成）**：按决策产出结构化计划（步骤 + 依据）。
- **verify（审核）**：先由服务端硬规则裁决，再由模型做事实依据复核；**规则结论优先，模型结论只能加严不能放宽**。

拆成三次的理由：单次调用同时做决策+规划+自审时，模型倾向于自我背书（自审等于没审）。分阶段后 verify 阶段看到的是另一次调用的产出去审核，审核才有意义。

## 2. 端点

```
POST /api/agent/pipeline
Content-Type: application/json
body: { "prompt": "<自然语言意图，≤ 2000 字符>" }
```

- 请求体上限沿用 runtime.mjs 现有 8192 字节。
- **必须在真实硬件模式（isHardware=true）下允许调用**。因此不得把 `/api/agent/pipeline` 加入 gateway/runtime.mjs 第 163 行的 hardware 禁列（该禁列只针对会产生模拟执行副作用的 `/api/device`、`/api/command`、`/api/demo/scenario`、`/api/agent/plan`）。
- 本管线是**只读**的：不执行设备动作、不写硬件历史、不写分析历史。
- 模型未配置或调用失败：返回 200 + `audit.verdict="needs_human"` 且对应 stage `state="failed"`，让原生端能显示失败原因；不要用 5xx 让原生端只拿到空错误。

## 3. 响应结构

字段名与枚举值锁定，不得改写。数值一律为 number，缺失用 `null`（不要用 `undefined` 或省略字段）。

```ts
interface AgentPipelineResult {
  kind: "agent_pipeline";
  pipelineVersion: 1;
  traceId: string;                 // 非空，短标识即可
  requestedAt: number;             // epoch ms
  prompt: string;
  mode: "simulation" | "hardware";
  provider: string;
  model: string;
  calls: number;                   // 实际发生的模型调用次数 0..3
  executed: false;                 // 恒为 false
  hardwareControl: false;          // 恒为 false
  stages: Stage[];                 // 恰好 3 条，顺序固定 decision, generate, verify
  decision: Decision | null;
  plan: Plan | null;
  audit: Audit;
  memory: Memory;
}

interface Stage {
  stage: "decision" | "generate" | "verify";
  state: "passed" | "blocked" | "failed";
  startedAt: number;
  finishedAt: number;
  durationMs: number;
  summary: string;                 // 一句话，≤ 300 字符，可直接显示
  error: string | null;            // 失败时为稳定错误码，如 "model_unavailable" / "timeout" / "invalid_output"
}

interface Decision {
  intent: string;                  // ≤ 200 字符
  situation: string;               // ≤ 500 字符，对环境快照的判读
  confidence: number;              // 0..1
  riskLevel: "low" | "medium" | "high";
  candidates: Candidate[];         // 0..4 条
  openQuestions: string[];         // ≤ 3 条
}

interface Candidate {
  action: string;                  // 必须在动作白名单内
  reason: string;                  // ≤ 500 字符
  riskLevel: "low" | "medium" | "high";
  requiresConfirmation: boolean;   // 由服务端按第 4 节分级写入，不由模型决定
  maxRunMs: number | null;         // 非 ventilate 类为 null
}

interface Plan {
  summary: string;                 // ≤ 2000 字符
  steps: PlanStep[];               // 0..4 条
  evidence: Evidence[];            // ≤ 8 条
}

interface PlanStep {
  action: string;                  // 必须在动作白名单内
  reason: string;                  // ≤ 1000 字符
  requiresConfirmation: boolean;   // 同 Candidate，服务端分级写入
  maxRunMs: number;                // ventilate 为 1000..20000 整数；其余沿用 20000
  processed: false;
}

interface Evidence {
  ref: string;                     // 真实快照字段路径，如 "env.co2"
  value: string | number | boolean | null;
  observedAt: number | null;       // epoch ms，无时间戳为 null
  fresh: boolean;                  // 是否在时效窗口内（15s）
}

interface Audit {
  verdict: "allow" | "block" | "needs_human";
  reasons: string[];               // ≤ 6 条，可显示
  ruleHits: RuleHit[];
  missingEvidence: string[];       // ≤ 5 条
  modelVerdict: "allow" | "block" | "needs_human" | "unknown";  // 模型结论，仅作参考
  authoritative: "rules" | "model"; // 最终结论以谁为准
}

interface RuleHit {
  ruleId: string;
  passed: boolean;
  detail: string;                  // ≤ 200 字符
}

interface Memory {
  used: number;                    // 引用的历史条数
  sources: string[];               // 如 ["analysis-history:12"]
}
```

## 4. 审核分级（本项目的核心安全口径）

用户已明确拍板：**风险高的才要人工审核，风险不高的直接通过**。落地规则如下，顺序即优先级：

### 4.1 硬规则（命中任一 → `verdict="block"`，`authoritative="rules"`）

规则来源必须与 `openharmony/entry/src/main/ets/services/SafetyEngine.ets` 一致，不得自行发明阈值：

| ruleId | 判定 | 说明 |
|---|---|---|
| R-ESTOP | 急停生效 | 硬件断电优先，不可豁免 |
| R-SENSOR-OFFLINE | 传感器离线 | `!sensorOnline` |
| R-SAMPLE-STALE | 采样时间戳非有限值、晚于 now+1000ms、或超过 15000ms 未更新 | 超出 15s 时效即视为不可决策 |
| R-CO-INVALID | CO 非有限或 < 0 | 读数非法 |
| R-CO2-INVALID | CO₂ 非有限或 < 0 | 读数非法 |
| R-CO | CO ≥ 30 | **软件演示阈值，不是国标**，文档里不得写成健康标准 |
| R-CO2 | CO₂ ≥ 1500 | 同上 |
| R-ACTION | 任一步骤/候选动作不在白名单 | 白名单 = `query_environment`、`request_access`、`ventilate`、`stop_ventilation` |
| R-PLAN | 计划结构非法（超 4 步、summary/reason 超长、ventilate 的 maxRunMs 不在 1000..20000 整数） | 与 gateway/agent.mjs 的 validatePlan 同源 |

### 4.2 分级转人工（无硬规则命中时）

- `riskLevel === "high"` **或** `confidence < 0.7` → `verdict="needs_human"`
- 其余 → `verdict="allow"`，`requiresConfirmation=false`，**不需要人工点确认，直接放行**

### 4.3 阶段失败

任一 stage `state==="failed"` 时，最终 `verdict` 不得为 `allow`：安全相关阶段（decision/verify）失败降级为 `needs_human`，结构非法（R-PLAN/R-ACTION）降级为 `block`。

### 4.4 模型越权

模型 `modelVerdict` 与规则冲突时以规则为准（`authoritative="rules"`）；模型说 allow 而规则 block，必须仍然是 block。这条要有测试证明。

## 5. 三阶段职责与预算

- decision：输入 prompt + 当前环境快照 + 最近历史（≤8 条，只读），产出 Decision。
- generate：输入 Decision + 环境快照 + 依据，产出 Plan；evidence 的 `ref` 必须能在真实快照里查到同名值，禁止编造。
- verify：输入 Decision + Plan + 服务端规则结果，产出 modelVerdict 与 missingEvidence；随后服务端合成最终 Audit。
- 单次模型调用超时 ≤ 12s，整体预算 ≤ 40s；超时不重试式死循环，直接记该 stage `failed` 并返回。
- 模型输出必须经结构化校验后再用；解析失败记 `invalid_output`，不要把半结构化文本透给原生端。

## 6. 记忆

复用现有分析历史（`/api/agent/history` 背后的存储）作为记忆源，**只读**：不新增写盘、不污染既有历史。`memory.used` 为实际引用条数，`sources` 标明来源。会话内上下文由原生端维护，不占云端存储。

## 7. 原生侧契约

- `GatewayLink.ets` 新增 `pipeline(prompt: string): Promise<AgentPipelineResult>`，走 `POST /api/agent/pipeline`，超时与响应上限按 pipeline 单独放宽（读取超时对齐 plan 档、响应上限 100000 沿用）。
- 模型类型加在 `model/AgentModels.ets`，字段与第 3 节逐字对应。
- 界面按第 4 节结论呈现：三张阶段卡片（state 色点 + summary + durationMs）、verdict 徽标（allow 绿 / needs_human 琥珀 / block 红）、ruleHits 明细、missingEvidence。
- 只做增量，不重写既有布局与既有能力；加载中与失败必须有可见文案，不得静默失败。

## 8. 红线

- `executed` 与 `hardwareControl` 恒为 false；管线只出建议，任何时候都不下发设备指令。
- 禁止 Web 套壳 / H5 混合 / Flutter / React Native；原生侧只用 ArkTS + ArkUI。
- 模型密钥只留在服务端，不进原生代码、不进聊天、不进文档。
- 阈值只用于软件演示，文档中不得声称是国标或医疗/安全认证标准。

## 9. 变更流程

任一方发现契约不可实现（字段缺失、语义冲突），先停下并向 lead 报告冲突点与建议改法，由 lead 更新本文件；**不得单方面改动已锁定的字段名或枚举值**。
