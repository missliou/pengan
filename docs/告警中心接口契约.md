# 告警中心接口契约（ALERT-CENTER-20261103）

版本：1。定稿：2026-11-03，由调度 Agent（lead）写入并冻结；gateway 与 admin-ui 两侧按本文件并行实现。
用户已拍板的口径：①合并键＝设备+类型+子通道；同一未恢复告警持续发生只累加「最近发生」与次数，恢复后再次发生才新建记录；②「模型任务失败」只在同设备后续任务成功时判恢复，无成功证据则一直未恢复；③容量上限 2000 条（未恢复+已恢复合计），超限写入返回 alert_store_full 且保留全部旧记录；④演示模式跟随站点既有演示开关，样例显式标注，演示模式下确认/备注禁用且不调真实写接口。

## 1. 范围与非目标

- 范围：`gateway/alerts.mjs`（新建）、`gateway/cloud-server.mjs` 接线与生产者钩子、`admin-ui/src/pages/alerts.js`（新建）、`admin-ui/src/{app.js,lib/api.js,lib/data-source.js,styles.css}`、`admin-ui/dist`（重建）、两侧测试与各自交接。
- 非目标：任何设备控制下发；原生 HAP / `openharmony/` / `firmware/` 一律不改；不写 `待办.md`、`进度.md`（由 lead 汇总）；不改他人锁文件；不把网页嵌入原生应用。
- 现有能力不重复建设：设备会话/令牌/设备隔离复用 `DayuIngress`；管理员会话/角色/CSRF/Origin/审计复用 `CloudSecurity` + `history`；模型任务记录复用 `PipelineTasks`；故障判定是本轮新增的独立模块。

## 2. 数据模型

### 2.1 告警类型（固定枚举，落盘不可变）

| type | 中文名 | 判定来源 | severity |
|---|---|---|---|
| `device_offline` | 设备离线 | 该设备曾有会话，最近一帧年龄 ≥ 60s | high |
| `telemetry_stale` | 遥测数据过期 | 最近一帧年龄 ∈ [10s, 60s) | high |
| `collection_error` | 采集异常 | 快照 reason ∈ {invalid_hsp_sample, hardware_read_failed, hardware_file_too_large, invalid_receive_time, unknown} | medium |
| `sensor_channel_invalid` | 传感器通道无效 | quality.temperatureValid/humidityValid 或 gasValid 为 false 且设备在线 | medium |
| `model_task_failed` | 模型任务失败 | 模型任务 status=failed 或模型调用抛出非良性错误 | medium |

严重程度按类型固定（不随次数升级），便于统计口径可解释：`device_offline`、`telemetry_stale` 为 high；其余为 medium。枚举另保留 `low`、`critical` 供将来使用，本轮不产生。

### 2.2 合并键 subject

- `device_offline` → subject = `session`（每设备一条）。
- `telemetry_stale` → subject = `session`（每设备一条）。
- `collection_error` → subject = 快照 reason 原字符串（不同故障原因分开计）。
- `sensor_channel_invalid` → subject = `th` 或 `gas`（两个通道分开计）。
- `model_task_failed` → subject = `pipeline`（每设备一条，所有模型失败合并）。
合并键 = gatewayId + type + subject。同一合并键在未恢复期间只累加，不新建。

### 2.3 状态机与字段

state ∈ `open`（发生中未确认）、`acknowledged`（发生中已确认）、`recovered`（已恢复）。
- 首次发生 → open。管理员确认 → acknowledged；确认只写确认记录，不改变故障是否仍然发生。
- 故障消失 → recovered，写 recoveredAt 与恢复依据；recovered 不因确认而回退，确认也不因 recovered 而失效。
- 再次发生（同合并键）→ 新建 alertId，occurrences 从 1 重新计。

记录字段（持久化并对外返回）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `alertId` | string | `alert_` + uuid，不可复用 |
| `gatewayId` | string | 设备隔离键 |
| `type` / `subject` | string | 见 2.1 / 2.2 |
| `title` | string ≤120 | 中文可读标题 |
| `severity` | enum | low/medium/high/critical |
| `state` | enum | open/acknowledged/recovered |
| `acknowledged` | boolean | 与 state 正交，recovered 后仍可为 true |
| `revision` | integer | 每次发生累加/确认/备注都 +1；并发校验依据 |
| `firstAt` / `lastAt` | integer ms | 首次发生 / 最近发生；从未收到数据不产生记录，故不伪造时间 |
| `recoveredAt` | integer ms 或 null | 恢复时间 |
| `occurrences` | integer | 合并次数（同一未恢复期间） |
| `basis` | object | `{code, detail≤300, observedAt, sampleAgeMs, ttlMs}` 判定依据 |
| `evidence` | array ≤6 | `{ref, value, observedAt, fresh}` |
| `acks` | array | `{at, actor, note}` 确认记录（不可覆盖） |
| `notes` | array | `{at, actor, text}` 处理备注时间轴（只追加） |
| `relatedTaskIds` | array ≤5 | 关联模型任务 |
| `sample` | boolean | 演示样例标记，真实数据恒 false |
| `executed` / `hardwareControl` | boolean | 恒 false：告警中心不下发设备控制 |

## 3. 故障派生（生产者）

`deriveFaults(inputs, now)` 是纯函数，输入由调用方注入，便于测试控制时间：

```text
inputs = {
  devices: [{gatewayId, hasSession, lastAcceptedAt, snapshot:{deviceOnline, reason, receivedAt, sampleAgeMs, quality:{temperatureValid,humidityValid,gasValid}}}],
  tasks: [{gatewayId, taskId, status, error, finishedAt, startedAt}],
}
TTL_MS = 10000（复用 hsp-telemetry 的 HSP_TTL_MS），OFFLINE_MS = 60000。
```

规则：
1. `hasSession === false`（正常启动尚未收到数据）→ 不产生任何告警；列表响应 source.connected=false，UI 显示「未连接/未确认」。
2. 帧年龄 age = now - lastAcceptedAt：age < TTL → 无 stale 故障；TTL ≤ age < OFFLINE_MS → `telemetry_stale`；age ≥ OFFLINE_MS → `device_offline`（此时不再同时产出 stale，避免重复）。
3. snapshot.reason ∈ 采集异常集合 → `collection_error`（subject=reason）。reason=`read_only_hardware` 属正常只读硬件，不产生告警。
4. 设备在线且 quality 某通道 false → `sensor_channel_invalid`（subject=th/gas）。
5. tasks 中 status=failed 且 error 不在良性集合 → `model_task_failed`（subject=pipeline）；良性集合 = {ai_busy_try_later, invalid_prompt, device_session_changed, gateway_required, alerts 相关输入错误}。安全规则正常拒止（audit.verdict ∈ block/needs_human）不是模型调用失败，禁止因此产生告警。
6. 无法判断（reason 未知且无时间证据）→ 归入 `collection_error` 且 basis.code=`unknown_reason`，不允许瞎猜成离线或过期。

恢复证据：`telemetry_stale`/`device_offline` 以「收到新鲜帧（age < TTL）」为恢复；`collection_error`/`sensor_channel_invalid` 以「本次派生不再出现该故障」为恢复；`model_task_failed` 以「同设备后续任务 status=completed」为恢复，无成功任务则保持未恢复。

## 4. 持久化

- 复用 `CloudHistory` 追加链：每次状态变化写一行 `{kind:'audit', gatewayId, data:{event:'alert_state', scope:'alert', actor, alert}}`，`alert` 为该告警的完整快照。
- 行类型取 `audit` 是**契约 v1.1 的修订**：`gateway/cloud-history.mjs` 的 kind 白名单只接受 telemetry/analysis/audit，新增 kind 会破坏既有链校验；`pipeline_state`、`human_review_saved` 同样走 `audit` + 独立 event 名，事件名已足够区分，哈希链、设备隔离、容量与重放全部继承。
- `open()` 重放 `history.rows` 中 `kind==='audit' && data.event==='alert_state' && data.scope==='alert'` 的行重建内存索引，按 alertId 保留最新一版；重启后状态、确认、备注完整恢复。
- `occurrences` 只由**故障观察**累加（采集入库帧、模型任务事件），由 GET 触发的 reconcile 只做状态迁移（开启/恢复），不得增加 occurrences，否则统计会被读取行为污染。
- 落盘节流：同一未恢复告警的纯发生累加可在内存逐次累加、落盘最多 10s 一次（导出常量 `ALERT_MERGE_WRITE_INTERVAL_MS`）；首次发生、恢复、确认、备注必须立即落盘，不得节流。崩溃最多丢失一个节流窗口内的发生次数，`firstAt` 不受影响。
- 容量：告警记录数上限 2000；新建告警超过上限时抛 `alert_store_full`，**不淘汰任何旧记录**，接口按 5.4 映射返回错误，UI 必须显示失败而不是成功。
- 单条告警事件上限 200（确认+备注+发生累加），超限抛 `alert_event_limit`。
- 写入失败（history.append 抛错）必须向上抛出 `alert_persist_failed`，响应中不得出现 saved:true 或成功文案。
- 派生失败不得影响采集与模型链路：ingest / 任务完成时的 reconcile 为 best-effort，失败把错误码记入内存 `lastReconcileError`，列表响应 source.lastReconcileError 回传（只放错误码，不放堆栈与密钥）。

## 5. HTTP 接口

全部挂在既有管理端鉴权之后（会话 Cookie + 写操作 `x-pengan-csrf` + Origin 校验），设备隔离用既有 `selected(params)` 解析 `gatewayId`（未知设备 → `gateway_required`）。

### 5.1 GET `/admin-api/alerts`

查询参数：`gatewayId`、`type`、`severity`、`status`（open|acknowledged|recovered）、`cursor`（上次响应的 nextCursor）、`limit`（默认 20，1..100）。非法取值 → `invalid_alert_query`。

响应：

```json
{
  "schemaVersion": 1, "scope": "alerts", "generatedAt": 0, "gatewayId": "...",
  "filters": {"type": null, "severity": null, "status": null},
  "counts": {"all": 0, "open": 0, "acknowledged": 0, "recovered": 0, "bySeverity": {"low":0,"medium":0,"high":0,"critical":0}},
  "countBasis": {"all":"该设备全部告警（含已恢复）","open":"发生中且未确认","acknowledged":"发生中且已确认","recovered":"已恢复，不再计入未处理"},
  "source": {"connected": true, "lastAcceptedAt": 0, "lastReconcileError": null, "evaluation": "derived-on-read"},
  "items": [ { "alertId":"alert_...", "type":"device_offline", "subject":"session", "title":"设备离线", "severity":"high", "state":"open", "acknowledged":false, "revision":1, "firstAt":0, "lastAt":0, "recoveredAt":null, "occurrences":1, "basis":{"code":"stale_frames","detail":"...","observedAt":0,"sampleAgeMs":0,"ttlMs":10000}, "ackCount":0, "noteCount":0, "sample":false } ],
  "nextCursor": "s12" , "truncated": false
}
```

`counts` 是**过滤后**集合的计数，`countBasis` 给出中文口径文案，UI 必须原样展示，不得自造统计。游标为不透明字符串 `s<seq>`，仅服务端可解释；到末页 `nextCursor=null`。排序：lastAt 降序，seq 降序 tiebreak。

### 5.2 GET `/admin-api/alerts/{alertId}`

返回单条完整记录（含 acks、notes、evidence、relatedTaskIds）。不存在或跨设备 → `alert_not_found`。

### 5.3 POST `/admin-api/alerts/{alertId}/ack` 与 `POST /admin-api/alerts/{alertId}/note`

请求体：ack 为 `{expectedRevision:number, note?:string(≤500)}`；note 为 `{expectedRevision:number, text:string(1..500)}`。多余字段、类型不符、超长 → `invalid_alert_note`。

规则：
- 角色必须是 admin（`security.requireRole(session,'admin')`），viewer → 403（复用既有 forbidden 映射）。服务端实际校验，不靠 UI 隐藏。
- 幂等键 `alertId|action|expectedRevision|sha256(text或note)`：命中已成功记录 → 返回 `duplicate:true` + 当前 alert，不新增记录。校验幂等在前、revision 校验在后，保证「精确重试」安全。
- `expectedRevision` 不等于当前 revision → `alert_revision_conflict`（409），提示重新读取；不同管理员并发提交不同内容也走此错误。
- 确认不改变 state 的发生状态（open → acknowledged 仅在未恢复时），不产生恢复，不下发设备控制。
- 备注只追加，禁止覆盖既有 notes 或 acks。
- 响应：`{schemaVersion:1, alert:AlertFull, duplicate:boolean, executed:false, hardwareControl:false}`。

### 5.4 错误码与状态映射

| code | HTTP | 含义 |
|---|---|---|
| `invalid_alert_query` / `invalid_alert_note` | 400 | 参数非法 |
| `forbidden` / `csrf_required` / `origin_denied` | 403 | 权限/CSRF/Origin（沿用既有映射） |
| `alert_not_found` | 404 | 不存在或跨设备 |
| `alert_revision_conflict` | 409 | 版本冲突，需重读 |
| `alert_persist_failed` | 503 | 写入失败，未保存 |
| `alert_store_full` / `alert_event_limit` | 507 | 容量上限，未保存、未淘汰 |

错误响应沿用既有 `{error: code}` 形态；日志与响应不得包含模型密钥、设备令牌、家庭 Wi-Fi 密码（沿用 cloud-history 字段黑名单）。

## 6. Web 交互契约（admin-ui）

1. 导航：`app.js` 新增「告警中心」，与既有页面同构注册；导航点显示未处理数量（counts.open + counts.acknowledged），切换设备时刷新。
2. 统计区：展示 all/open/acknowledged/recovered 与分严重程度，口径文案直接取 countBasis；无数据显示「未连接」，不显示 0 冒充正常。
3. 列表：筛选（类型/严重程度/状态）、游标分页（下一页/返回首屏）、每项显示设备、类型、最近发生时间、状态徽标；空态文案「暂无告警（未虚构）」。
4. 详情：判定依据 basis、occurrences、firstAt/lastAt/recoveredAt 与恢复情况、确认记录、备注时间轴（时间/处理人/内容）。
5. 确认/备注：admin 可见可提交，viewer 只读；提交中禁用按钮防重复；失败显示「未确认」并保留输入；409 提示重新读取后重试。
6. 轮询：15s 一次，只更新统计与列表区域（用独立容器替换），**不重建详情输入框、不重放入场动画**；页面卸载、切页、切设备、退出登录立即清理定时器与 AbortController，迟到响应按 generation 丢弃。
7. 演示模式：跟随站点既有演示开关；样例数据带 `sample=true` 徽标并显示「样例」；演示模式下确认/备注按钮 disabled，不调用真实写接口。
8. 后端不可达时显示「后端未连接」，不得把 fetch 失败渲染成空列表或 0 告警。
