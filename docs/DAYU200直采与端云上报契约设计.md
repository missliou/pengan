```text
HH-HSP101（板子）      ：采集温湿度与 MQ-2 ADC，提供局域网只读 HTTP 遥测，本地 OLED 显示。不直连模型。
```

## 3. 链路 A：DAYU200 直读 HH-HSP101 遥测

### 3.1 端点与请求

【已核实，来自 `firmware/hh-hsp101/src/dash_provision.h:57` 与 `dashboard.c:120-127`】

- 端点：`GET http://<板子局域网IPv4>:80/api/pengan/telemetry`
- 响应：`application/json`，`Cache-Control: no-store`，`Connection: close`，单次响应体上限 512 字节。
- 板子采样尚不可用时返回 `503`，正文 `{"error":"telemetry_unavailable"}`；这条通道没有认证，也没有 TLS。
- 板子默认以 SoftAP 起网（`board_config.h`：SSID `HH-HSP101-Monitor`，频道 6，`DASH_WEB_PORT 80`），配网成功后作为 STA 加入家庭局域网并取 DHCP 地址。默认热点口令见固件配置与 `待办.md`，本文件不复述。

【已核实，电脑桥的既有约束，建议原生端逐条对齐 `gateway/hsp-http.mjs`】

- 只允许 RFC1918 私网 IPv4（`10/8`、`172.16-31`、`192.168/16`），其他一律拒绝。
- 拒绝重定向（`redirect: 'error'`）、禁用缓存（`cache: 'no-store'`）。
- 单次请求 3 秒超时；响应体超过 4096 字节即取消并判定失败。
- 取回耗时≥3 秒的样本直接丢弃（视为 `wifi_sample_too_slow`），不进入历史。

原生端对应实现要点：`@ohos.net.http` 的 `connectTimeout: 3000 / readTimeout: 3000`、`expectDataType: STRING`，并在业务层校验响应字节数与状态码。OpenHarmony 的 HTTP 模块不保证等同于 Node 的 `redirect:'error'` 语义，【待确认】需实测 `resize`/重定向行为，若无法禁止重定向，则在原生侧改为固定 IP 白名单 + 响应体字段全量校验作为兜底。

### 3.2 帧字段与校验

【已核实，固件 `dash_pengan_json` 与 `gateway/hsp-telemetry.mjs:validateHspFrame`】

| 字段 | 类型/范围 | 含义与校验 |
|---|---|---|
| `schemaVersion` | 固定 `1` | 不匹配即拒绝整帧 |
| `deviceId` | 固定 `"hh-hsp101-001"` | 身份白名单，不匹配即拒绝 |
| `simulated` | 固定 `false` | 真实链路禁止模拟标记 |
| `controlSupported` | 固定 `false` | 无执行器，禁止下发控制 |
| `coValid` / `co2Valid` | 固定 `false` | 无 CO/CO₂ 硬件 |
| `coPpm` / `co2Ppm` | 固定 `null` | 缺值为未知，不做 ADC 换算 |
| `uptime_ms` | uint，`0..4294967295` | 上电毫秒，用作帧去重与重启检测 |
| `th_ok` | bool | 温湿度通道是否有效 |
| `temperature10` | int，`-400..850` | 实际值 = 该值 ÷ 10 ℃ |
| `humidity10` | uint，`0..1000` | 实际值 = 该值 ÷ 10 % |
| `gas_ok` | bool | MQ-2 通道是否有效 |
| `gas_raw` | int，`0..4095` | 12 位 ADC 原始值 |
| `gas_mv` | int，`0..7200` | 对应毫伏 |
| `th_sample_age_ms` | uint | 板侧采样时刻距今毫秒 |
| `gas_sample_age_ms` | uint | 同上，气体通道 |

校验规则（严格按基线代码，不要自行加严或放宽）：

- 身份/结构类不符（`schemaVersion`、`deviceId`、`simulated`、`controlSupported`、`coValid`/`co2Valid` 非 `false`、`coPpm`/`co2Ppm` 非 `null`）→ `invalid_hsp_identity`，整帧拒绝。
- `uptime_ms` 与两个 `*_sample_age_ms` 必须是 `0..4294967295` 的整数，缺失或越界 → `invalid_hsp_quality`，整帧拒绝。
- **数值范围只在对应通道 `*_ok` 为真时检查**：`th_ok=true` 而 `temperature10`/`humidity10` 越界 → `invalid_hsp_climate`；`gas_ok=true` 而 `gas_raw`/`gas_mv` 越界 → `invalid_hsp_adc`。
- 当 `*_ok=false` 时，基线校验器**不检查**该通道数值，板侧可能带残值。接收方必须把该通道数值强制置空、显示未知，**不得因为残值"看起来合理"就采信，也不得因为残值超出正常范围就整帧拒绝**——两种做法都与现有实现不一致，会造成端云两套校验漂移。
- 不沿用上一帧的"正常"值：通道不可用就是未知。

配套测试向量见 `docs/DAYU200遥测帧校验向量.md`，实现端侧与云端校验时必须复用同一组期望结果。

注意：帧字段顺序与 `hsp-http.mjs` 的白名单键顺序不完全一致（固件把 `simulated` 与 `uptime_ms` 相邻），原生端必须按 JSON 语义逐字段取值，禁止依赖字节位置或字符串截取。

### 3.3 时效、来源与"未知"语义

【已核实，`gateway/hsp-telemetry.mjs`】

- 全局时效 `HSP_TTL_MS = 10000`（10 秒），以接收方本地墙钟计算 `age = now - receivedAt`。
- `age ≥ 10s` → 整帧判为 `telemetry_stale`，显示未知、拒止真实准入。
- 通道级年龄：`thAge = age + th_sample_age_ms`、`gasAge = age + gas_sample_age_ms`，各自 `< 10s` 且对应 `*_ok` 为真才可用。
- 现有 `GatewayLink.ets:readHardware()` 还额外实现"同一 `receivedAt` 长时间不变"的重复帧保护（≥10 秒未更新抛错），这是防止网络恢复后旧样本冒充新数据的必要检查，迁移到直采时必须保留。

【待确认，需决策】原生直采时"接收时间"只能取 DAYU200 本地墙钟。板子没有可靠时钟，因此**不能信任板侧绝对时间戳**，只能信任 `*_sample_age_ms` 这类相对量。这一点必须在实现与文档里写死，避免把相对年龄当绝对时间。

- `source` 取值：现有实现为 `serial` / `http`。直采链路新增取值建议为 `dayu-direct`（或复用 `http` 并以独立的 `transport` 标记区分），【待确认】由协调者定，因为它会影响 `docs/设备通信协议.md`、报告导出字段与既有测试。

### 3.4 帧去重与重启检测

【已核实】电脑桥用 `uptime_ms` 与上一帧相同来判重复（`duplicate: true`），不刷新 `receivedAt`。

问题：`uptime_ms` 是上电相对值，**板子重启后会归零并重新递增**，与上一帧数值相同不足以证明是新样本，重启后也可能出现单调性被破坏。现有 MQTT 协议草案（`docs/设备通信协议.md`）设计了 `bootId`，但 HTTP 遥测帧里**没有** `bootId`。

【待确认】三选一，按代价从低到高：
1. 原生侧自合成会话标识：以"首次看到该帧时连接上板子的本地时刻 + 首次 `uptime_ms`"生成 `sessionBootId`，不上报给板子，只用于本地上报去重。零改动固件，立即可做。
2. 固件增加 `bootId`（随机 UUID 或上电唯一值）并在 `validateHspFrame` 与原生校验同步放宽范围。**改动固件 + 网关 + 测试**，属于跨所有权改动，须先交接口说明给该文件负责人。
3. 云端以 `(deviceId, uptime_ms)` 单调窗口判重并容忍回绕。最省事但语义最弱。

本设计**默认推荐方案 1**，因其不触碰固件与网关共享文件，且不引入未验证假设。

### 3.5 轮询、断网与恢复策略

建议参数（全部对齐电脑桥已验证过的量级，不新造更激进的值）：

- 前台轮询间隔：2 秒（与现有 2 秒只读刷新一致）。
- 单次失败：不立即报错，允许连续 2 次超时再判离线，避免 UI 抖动。
- 离线判定：`age ≥ 10s` 或连续失败 → 界面显示"未知/拒止"，同时作废进行中的分析结果（现有实现已有 `revision`/`connectionEpoch` 机制作废旧响应，直采必须复用同一语义）。
- 恢复判定：只有校验通过且 `uptime_ms` 相对上一帧前进（或按 3.4 判为新会话）的**新帧**才允许重新显示读数。
- 板子地址变化：DHCP 重分配会让 IP 失效。建议原生配置页保留"手动填写板子 IP"+ 连接状态自检，并如实提示"获取局域网 IP 不等于互联网可达"（固件配网页已明确此点）。【待确认】是否需要局域网扫描以自动发现板子，属于新增功能，需用户决定是否排期。

### 3.6 后台行为（当前明确缺口）

【已核实】`openharmony/entry/src/main/module.json5` 仅声明 `ohos.permission.INTERNET` 与 `ohos.permission.CAMERA`，`abilities` 里没有 `continuousTask` 配置。

结论：**现阶段应用退到后台后能否持续轮询板子并未验证**。要在后台持续采集，需要显式向系统申请持续运行能力，并在退出时释放。【待确认】是否本期启用后台采集，取决于评审是否需要"无人值守长时间记录"这一能力。

在决策之前，本设计规定：后台期间**不采集、不上报、不生成任何新数据点**；回到前台后按 3.5 的"新帧才可用"规则恢复，且断连期间无数据即无数据，**不得用空值或旧值补齐**。

### 3.7 与现有电脑桥的差异（迁移范围清点）

| 能力 | 现在（电脑桥） | 目标（DAYU200 直采） | 迁移代价 |
|---|---|---|---|
| 谁去拉板子数据 | `gateway/hsp-http.mjs` 在电脑轮询 | 原生 HAP 轮询 | 新增原生采集类，逻辑可参考移植 |
| 样本落盘位置 | 电脑 `tmp/runtime/hsp-latest` 文件 | 板子在网时仅内存 + 原生沙箱 | 需原生侧本地持久化方案 |
| 历史与哈希链 | 网关 `hardware-history.mjs` | 云端历史（见链路 B） | 新增上报与云端存储 |
| 帧校验 | 网关 JS | ArkTS 重复一套 | 存在双实现漂移风险，须用同一份测试向量固化期望值 |
| 配置入口 | 电脑网页 | 原生配置页 | 待实现 |

双实现漂移是这条链路最大的隐性风险：同一份帧校验规则会同时存在于 `.mjs` 与 `.ets`。建议在实现时用**同一组固定 JSON 样本**（含合法帧、越界帧、缺字段帧、重复帧）在两测各跑一遍，把期望结果写进测试而不是靠口头约定。

## 4. 链路 B：DAYU200 主动上报 Ubuntu 云端

### 4.1 为什么必须"端侧主动出网"

云端不能访问家庭私网 IP，这是 `规则.md` 第 5 条的硬约束。因此方向只有一种：**DAYU200 主动发起出站 HTTPS 请求**。云端不反查板子、不反查设备内网地址。NAT 穿透、内网映射等方案一律不采用。

### 4.2 上报接口（建议稿）

```text
POST https://<云端主机>/api/v1/telemetry/batch
Content-Type: application/json
Authorization: Bearer <设备令牌>
X-Pengan-Nonce:      <单次请求随机值>
X-Pengan-Sent-At:    <设备本地 UTC 毫秒>
```

请求体：

```json
{
  "schemaVersion": 1,
  "deviceId": "hh-hsp101-001",
  "gatewayId": "dayu200-<设备指纹>",
  "sessionBootId": "原生侧合成，见 3.4",
  "records": [
    {
      "receivedAt": 1762000000123,
      "transport": "dayu-direct",
      "frame": { "...": "3.2 白名单字段原样" }
    }
  ]
}
```

服务端响应：

```json
{
  "schemaVersion": 1,
  "accepted": 1,
  "duplicate": 0,
  "rejected": [{ "index": 0, "reason": "frame_invalid" }],
  "serverTime": 1762000000900
}
```

设计要点：
- `records` 有界（建议单批 ≤ 50 条，与现有"最近 50 条采集"窗口一致），超限必须分批，禁止静默截断后仍报成功。
- 只上报 3.2 的白名单字段。**配网凭据、家庭 SSID、密码、OLED 状态、歌曲/页面展示等一律不出设备**（现有电脑桥已按同一原则做键白名单裁剪，`hsp-http.mjs:33`，直采必须延续）。
- 去重键：`(deviceId, sessionBootId, uptime_ms)`。服务端按此判 `duplicate`，客户端可安全重放同一批而不产生重复记录。
- 客户端在收到 2xx 且 `accepted + duplicate == 提交条数` 时才清除待发队列；其余情况保留待发。

### 4.3 设备身份与传输保护（现状 = 未设计未实现）

必须诚实区分三件事，**任何一件都不能代替另一件**：
1. HAP 签名：证明包来源，属于发布环节；
2. 设备身份认证：证明"这个请求确实是那台 DAYU200"，本链路目前**没有**；
3. 数据加密：TLS 保护传输，本链路**尚未部署**。

`规则.md` 第 6 节明确"签名 HAP 不等于业务设备身份认证"，也不能因为代码目录里存在证书或调用了加密 API 就声称安全验收通过。

【待确认，需用户/协调者决策的开放项，本设计不擅自定案】
- 令牌签发方式：出厂预置 / 云端人工建号后由原生配置页录入 / 一次性配对码交换。三者的运维复杂度与安全性差异明显。
- 令牌存储：是否使用 OpenHarmony 密钥存储类能力，需在目标 API 版本与 DAYU200 实际系统上核实可用性；未经核实不写入代码。
- HTTPS 证书与主机：云端域名、证书来源尚未确定。`ConnectionSettings.ets` 已有的规则"公网服务必须 HTTPS，HTTP 只允许本地或私网"应直接沿用为云端配置的强制校验。
- 时间戳与 nonce 的作用范围：仅作重放防护窗口（建议 ±5 分钟），**不能**当作设备身份。

### 4.4 离线、重传与数据量

- 断网期间：本地待发表按 `(deviceId, sessionBootId, uptime_ms)` 去重后排队；队列有上限（建议 2000 条），满时**丢弃最旧**并在上报元数据中带上丢弃计数，让云端能如实显示"记录不连续"。不得虚报完整性。
- 重试：指数退避（1s、2s、4s…上限 60s），单轮有总时长上限，避免持续消耗电量与蜂窝/局域网带宽。
- 真实模式缺值即未知：缺 CO/CO₂ 硬件就永远不上报浓度字段，MQ-2 的 ADC 不是浓度。

### 4.5 历史隔离

- 存储按 `deviceId` 分区；跨设备查询需显式授权，默认不合并。
- 沿用现有网关的完整性思路（追加式、哈希链、满或检测到截断/删除时冻结追加），在云端以相同语义实现，避免把可覆盖的表当作可信历史。
- 文字分析与图片分析的存储要与原始采集记录分开；照片只在用户主动点击后提交，不自动上传，也不自动入历史。

### 4.6 云端接入侧需实现的最小清单

1. TLS 终止与证书管理（部署方式待定）。
2. 鉴权中间件：校验设备令牌、nonce 窗口、按设备限流。
